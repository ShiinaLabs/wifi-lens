# Wi-Fi Link-State Source Audit

## Scope and method

This audit follows the live public-app implementation in `WiFiLensCore` and the WiFi Lens app target. It distinguishes raw observations from conclusions that callers or UI derive from them. File references below are repository-relative and include line numbers from the audited checkout.

## Source modules

- `WiFiLensCore/Sources/WiFiLensCore/Interfaces/NetworkInfoService.swift:152-166,248-289` discovers interfaces through `getifaddrs()` and `CWWiFiClient.interfaceNames()`, reads CoreWLAN interface properties, and optionally captures point-in-time link evidence. For Wi-Fi interface evidence it reads `interfaceMode()`, `powerOn()`, SystemConfiguration `State:/Network/Interface/<name>/Link` and `kSCPropNetLinkActive`, plus SSID/BSSID. The evidence object records source/cycle/time; a failed or absent read can remain unavailable rather than being synthesized as a negative.
- `WiFiLensCore/Sources/WiFiLensCore/Observation/Providers/WiFiCurrentConnectionProvider.swift:13-67` derives current status from the same-cycle interface snapshot. Its separate `isConnected` field is `ssid != nil`; the verified link assessment comes from `WiFiLinkInterpreter`, not SSID presence.
- `WiFiLensCore/Sources/WiFiLensCore/Observation/Models/WiFiCurrentStatus.swift:90-123` defines `WiFiLinkInterpreter`. It returns `.associated` only when evidence matches the expected snapshot cycle and capture time, mode is station, radio is `.reportedOn`, and `linkActive == true`. Missing, stale, false, unsupported, or contradictory evidence returns `.unknown`; it does not infer `.disconnected`.
- `WiFiLensCore/Sources/WiFiLensCore/WiFiPowerMonitor.swift:12-18,23-28,30-55,57-98` registers `WiFiPowerMonitor` as the `CWWiFiClient` delegate for `.powerDidChange`, refreshes state on `powerStateDidChangeForWiFiInterface`, and polls `powerOn()` every five seconds as a safety net. Its output concerns radio power/interface availability, not association or internet reachability.
- `WiFiLensCore/Sources/WiFiLensCore/Scanner/WiFiScanner.swift:83-165` runs repeated `scanForNetworks` calls with retry/backoff until its task is stopped. This full-spectrum network-discovery loop is separate from per-cycle current-link assessment, the power monitor, and both diagnostic path-monitor chains.
- `WiFiLensCore/Sources/WiFiLensCore/ScannerViewModel.swift:119-122,423-524,1023-1055,1057-1085` gates the live scan loop on authorization and Wi-Fi power. A denied authorization or a power/interface interruption stops scanning; publication eligibility also rechecks both before publishing a scan result. Normal `stop()` stops the observation runtime but does not stop the separately owned `WiFiPowerMonitor`; termination does stop it.
- `WiFiLensCore/Sources/WiFiLensCore/Observation/Runtime/WiFiObservationRuntime.swift:249-263,351-404,414-438` owns the shared scan source lifecycle, produces snapshots per scan cycle, and stops the source when scanning is stopped or publication is rejected.
- `WiFiLensCore/Sources/WiFiLensCore/Observation/Providers/RoamingProbeProvider.swift:7-36` reads current SSID/BSSID/channel/RSSI/bit rate from the current CoreWLAN interface. It sets `isConnected` to `ssid != nil` and sets `isWiFiPowerOn` to `true` whenever an interface object exists; it does not independently verify radio power or link association.
- `WiFiLensCore/Sources/WiFiLensCore/LocationPermissionManager.swift:9-23,25-57` owns Location Services authorization status required for SSID reads; it does not request or collect geographic coordinates.
- `WiFiLensCore/Sources/WiFiLensCore/NetworkConnectivityCheck.swift:24-98,105-167` implements a direct `NWPathMonitor` chain: `NetworkConnectivityCheck` asks `SystemNetworkPathChecker` for path status and path evidence. This is distinct from `NetworkFingerprint` observation and does not establish Wi-Fi association.
- `WiFiLensCore/Sources/WiFiLensCore/NetworkFingerprint.swift:292-328,370-431` uses a separate `NWPathMonitor` to build network fingerprints alongside DNS/proxy/route observations. Its sorted first usable interface is a deterministic fingerprint representative, not an authoritative system-selected or primary interface.
- `WiFiLensCore/Sources/WiFiLensCore/NetworkDiagnosticsViewModel.swift:303-338,510-538` starts the fingerprint observation for a diagnostic session, bounds initial acquisition, and ties cancellation to the diagnostic task. The diagnostic session has a 30-second budget (`:135-136`). Its default `NetworkConnectivityCheck` also uses the direct `SystemNetworkPathChecker` chain (`:208-216`; `NetworkConnectivityCheck.swift:24-68,105-167`).

## Summarized findings

### Uses SSID presence as a signal

- `OverviewView` and `InterfacesView` use non-nil SSID to select/display a Wi-Fi interface (`App/OverviewView.swift:20-22`; `Interfaces/InterfacesView.swift:39-41`).
- `RoamingProbeProvider` defines its `isConnected` value as `ssid != nil`, and `RoamingTestViewModel` uses that value plus a non-nil SSID as its readiness guard (`Observation/Providers/RoamingProbeProvider.swift:19-34`; `RoamingTestViewModel.swift:97-115`).
- `WiFiCurrentConnectionProvider` also sets its separate `isConnected` field from `ssid != nil` (`Observation/Providers/WiFiCurrentConnectionProvider.swift:40-65`). That field is not the verified link assessment: `WiFiLinkInterpreter` only returns `.associated` for evidence from the expected cycle and capture time, in station mode with the radio reported on and `Link.Active == true`. A missing/mismatched cycle or timestamp, unavailable/unsupported mode, radio not reported on, `Link.Active == false`, or unavailable `Link.Active` yields `.unknown`, never `.disconnected` (`Observation/Models/WiFiCurrentStatus.swift:90-122`).
- AP Radar uses BSSID, rather than SSID, to match a selected AP against scan observations (`APRadarViewModel.swift:365-394`).

### Uses power state, interface mode, `Link.Active`, or path state

- `powerOn()` is read by `WiFiPowerMonitor` to publish `.poweredOn` versus `.poweredOff` (`WiFiPowerMonitor.swift:58-69`) and by the point-in-time `NetworkInfoService` snapshot (`Interfaces/NetworkInfoService.swift:267-271`).
- `interfaceMode()` and SystemConfiguration `Link.Active` are captured as raw evidence by `NetworkInfoService` (`Interfaces/NetworkInfoService.swift:255-289`). `WiFiCurrentConnectionProvider` passes that evidence to `WiFiLinkInterpreter` with the snapshot cycle and capture time (`Observation/Providers/WiFiCurrentConnectionProvider.swift:40-65`). The interpreter reports `.associated` only for matching-cycle/time evidence with station mode, radio reported on, and `Link.Active == true`; all other cases, including `Link.Active == false`, are `.unknown`, not `.disconnected` (`Observation/Models/WiFiCurrentStatus.swift:90-122`).
- Two distinct network-diagnostics chains use `NWPathMonitor`: `NetworkConnectivityCheck` calls `SystemNetworkPathChecker` to get path status/evidence (`NetworkConnectivityCheck.swift:24-98,105-167`), while the session's `SystemNetworkFingerprintMonitor` uses `SystemNetworkPathFingerprintSource` for path-change fingerprints (`NetworkFingerprint.swift:292-328,370-431`). They do not establish Wi-Fi association. In both path-fingerprint code and diagnostic path evidence, sorting usable interfaces and taking `.first` yields a deterministic representative only; it is not a system-selected or primary-interface guarantee (`NetworkFingerprint.swift:310-328`; `NetworkConnectivityCheck.swift:60-85`).

### Uses a direct `CWWiFiClient` delegate

- `WiFiPowerMonitor.startMonitoring()` assigns itself to `CWWiFiClient.shared().delegate` and registers only for `.powerDidChange`; it removes that delegate and stops that event on stop/deinit (`WiFiPowerMonitor.swift:37-55,30-35`). The delegate method implemented is `powerStateDidChangeForWiFiInterface(withName:)`, which schedules a refresh (`:88-98`). The code does not register a separate event for SSID, association, or general link changes. A five-second `powerOn()` polling fallback is also active while the monitor runs (`:71-85`).
- The feature view models receive power-state changes via calls from their owner; they do not each install their own CoreWLAN delegate. The `WiFiScanner` discovery loop independently calls `scanForNetworks` and is not the mechanism that registers this power callback (`Scanner/WiFiScanner.swift:101-165`).

### Location authorization and collection

When live Wi-Fi authorization is required, `ScannerViewModel.start()` starts the power monitor, requests/refreshes Location Services authorization, and waits for a grant before starting the scan loop (`ScannerViewModel.swift:423-475`). Wi-Fi power-on reconciliation starts scanning only if authorized; denial calls `stop()` (`:498-523`). Before publication, `isRuntimePublicationEligible` rechecks authorization and stops the scan on denial (`:1057-1085`). The collection gate is for Wi-Fi data/SSID access, not geographic location tracking. The CLI observation below does not relax or prove this app-process permission gate.

### Can keep running after full-spectrum discovery scan stops

- Roaming’s independent timer/probe loop can continue after shared full-spectrum network discovery stops, unless the test is stopped or the power monitor reports a power/interface interruption (`RoamingTestViewModel.swift:134-168,193-218`; power handler at `:118-131`).
- AP Radar is an observation consumer of that shared runtime, so it gets no new scan observations after the runtime stops (`APRadarViewModel.swift:142-155,351-369`; `WiFiObservationRuntime.swift:249-263,414-438`). But the pulse scheduler’s `canPulse` predicate checks active/suspended/sound/target/smoothed-RSSI state—not scan liveness—so a stale pulse may continue until a separate lifecycle or power event stops it (`APRadarViewModel.swift:312-347`).
- Network Diagnostics uses its own path and fingerprint monitor chains and can operate while full-spectrum scanning is stopped; it is bounded by its session deadline and cancellation (`NetworkDiagnosticsViewModel.swift:303-338,510-538`; `NetworkConnectivityCheck.swift:24-68,105-167`; `NetworkFingerprint.swift:292-328`).
- `WiFiPowerMonitor` is also a separate power-state monitor, not a scan worker. Normal `ScannerViewModel.stop()` stops shared discovery but does not call `wifiPowerMonitor.stopMonitoring()`; termination does (`ScannerViewModel.swift:1023-1055`).

## What these APIs can and cannot establish

- **SSID non-nil is observed network-name data, not a universal association truth.** The app uses it as a positive signal in several places. Its absence can mean an unavailable/redacted/read-failed value or no reported SSID; it is not by itself proof that the radio is off or no Wi-Fi link exists.
- **`CWInterface.powerOn()` establishes CoreWLAN’s reported radio power state**, not that the interface is associated with an AP, has IP connectivity, or can reach the internet. Likewise, `interfaceMode()` classifies the operating mode (the code maps raw 1 to station and 0 to none/read-failure), not a successful association (`NetworkInfoService.swift:257-271`).
- **SystemConfiguration `Link.Active` is one link-state input, not a standalone association verdict.** The public observation pipeline only emits `.associated` when `Link.Active == true` is paired with same-cycle/same-capture evidence for station mode and radio reported on; `false`, missing, stale, or otherwise unusable evidence remains `.unknown` rather than `.disconnected` (`Observation/Models/WiFiCurrentStatus.swift:90-122`). It does not prove working IP configuration, gateway reachability, or internet access.
- **`NWPathMonitor` reports path status and usable interface characteristics**, not Wi-Fi-specific association or network name. `NetworkFingerprint` sorts path-usable interfaces and takes the first for a deterministic fingerprint; `NetworkConnectivityCheck` does the same for its path-evidence representative. Neither sorted-first result means system-selected or primary interface. A satisfied path may be routed through Ethernet, VPN, or another interface; path state is not an end-to-end reachability test (`NetworkFingerprint.swift:310-328`; `NetworkConnectivityCheck.swift:24-98`).
- **Direct CoreWLAN delegate events are power-change events here**, not general link/SSID change events. The monitor’s periodic refresh reduces dependence on receiving every callback, but observations remain sampled and are not a continuous ground-truth connection oracle (`WiFiPowerMonitor.swift:38-44,72-98`).
- **A standalone CLI tool running successfully does not prove the signed app has the same access.** Wi-Fi Link Lab explicitly describes itself as an independent experiment that does not run inside the WiFi Lens app sandbox and separates optional CLI-context permission changes from app-context changes (`tools/wifi-link-lab/README.md:1-3,36-39`). Its output is therefore evidence about the process that ran the experiment, not proof of what the signed app can observe. TCC/privacy decisions and sandbox entitlements are evaluated in the context of the executable/app identity; a different command-line executable is not evidence that WiFi Lens can read the same SSID or scan data.

## Signing configuration and entitlement interpretation

`WiFiLens/WiFiLens.entitlements:4-9` contains two temporary Mach lookup exceptions for `$(PRODUCT_BUNDLE_IDENTIFIER)-spks` and `-spki`; the file itself does not declare the app unsandboxed. The app target’s Debug and Release build configurations point `CODE_SIGN_ENTITLEMENTS` at this file and separately set `ENABLE_APP_SANDBOX = YES` and `ENABLE_HARDENED_RUNTIME = YES` (`WiFiLens.xcodeproj/project.pbxproj:2201-2215,2387-2402`). Therefore the source audit supports “sandbox and hardened runtime are enabled by the app target’s build settings,” not “the entitlement file proves unsandboxed.” Actual signed-product entitlements would require inspecting the built, signed app; this audit does not claim that step was performed.
